# ROADMAP.md — the source of all work

**This file is not optional.** Every feature the agent builds flows down
from here. If it isn't on this roadmap, it doesn't get built; if it needs
building, it gets added here first. One item ships per weekly cycle
(see `WEEKLY.md`).

`provisional: true` — the queue below was seeded at setup by the agent.
The human re-orders it.

## North star

EE Workcenter is the environment an agent steps into to take a KiCad
project from schematic to fabrication outputs with every gate green,
without a human running a tool by hand. Everything here serves that:
the toolchain installs itself, the gates are the definition of done, and
the skills tell the agent which gate comes next.

The owner's measure, 2026-11-10: a small model reaches the same working
design as a large one, and no electrical engineer has to find afterwards
what the gates left out. So what an engineer would ask lives in a gate
that runs it (corners, the frequency plan), and what comes next lives in a
command that says it (`workcenter next`), never in the reader's judgement.

## Feature Queue — ordered; top unblocked item ships next

### 1. A chip from RTL to a mask layout
- **Promise:** `workcenter chip gates <project>` takes a chip project (RTL, test benches, timing constraints, `chip.json`) through 10 gates in order on an open process: LINT, SIM, SYNTH, LAYOUT, STA, GLSIM, DRC, ANTENNA, LVS, EXPORT. The acceptance design, an 8-bit processor, reaches GREEN with `--strict` and a GDSII layout whose hash the gates judged.
- **Evidence:** The fixture chips under `tests/chips/`: 2 that pass, and 1 that fails for each gate from LINT to GLSIM; real reports of the engines for each failure of DRC, ANTENNA and LVS, and runs for what EXPORT refuses; the processor's gates report with its die size, its clock, and its least setup and hold slack with their corners; a small model that takes a chip of its own to GREEN with `workcenter next` alone.
- **Use case:** Design a chip from a spec (a new use case).
- **Scope guard:** Open engines and open processes only, 130 nm and 180 nm. GREEN says the open engines found no fault in the files. It does not say a foundry accepts the layout or that the silicon works: no foundry deck runs here, and a shuttle asks for more than a GDS. The first flow takes 1 clock, no memory macro and no analog block.
- **Status:** in progress on branch `claude/chip-design-jjyyxb`. The engines and the sky130A process kit install on request (`sudo ./install.sh --chip`). All 10 gates run. 138 tests hold the readers and each gate's judgement to real reports of its engine (`tests/test_chipflow.py`, `tests/test_chipfront.py`, `tests/test_chipback.py`). 9 fixture chips stand under `tests/chips/`: 7 that are red at 1 gate each, a counter that is GREEN with `--strict` in 42 s, and the acceptance processor, GREEN with `--strict` in 217 s on 4 processors. The processor is 760 cells and 132 flops on a die of 152.38 um by 152.38 um with a 40 ns clock; its least setup slack is 25.1717 ns at `max_ss_n40C_1v60` and its least hold slack 0.2974 ns at `min_ff_n40C_1v95`. Done on 2026-11-12: the build repairs slew, capacitance and antennas; the ledger of hashes keeps every entry at any count of jobs; every gate leaves a record of each file it read and wrote, and EXPORT asks all 9; SIM proves the benches with the project's list of changes; `workcenter next` names a chip's one next step, with the skills `chip-design` and `chip-gates` and the "Chip gates" section of `WORKCENTER.md`. Open: the small model's run; an attack on the gates' judgements by a reader who did not write them (P14 step 6); the chip branch on `main`.

### 2. A circuit walked stage by stage
- **Promise:** A command writes 1 page for a power or signal path from the project's decks and their corner records. Each stage is a chain: given, equation, computed value, the deck's measure with its span over the corners, what follows, and what the stage hands on. The range a stage is given is the range the stage before it hands on, and the command fails a page where the 2 differ. A node table gives each node's value under each condition, and every stage states its margin.
- **Evidence:** The page the reviewing engineer wrote by hand for Last Hit v0.16's power path (9 stages and a summary, on the project's branch `community/power-path-breadboard-notes`), written again by the command from the project's files with every number matching a fresh run. The thin margin that page found, a hardware trip at 6.17 A over a firmware limit of 6 A, is named by the command.
- **Use case:** Review a board before the bench (a new use case).
- **Scope guard:** The designer writes each equation in a writeup (P28). The command checks the chain and assembles the page. It derives nothing.
- **Status:** ready

### 3. A bench plan with the readings the decks predict
- **Promise:** A command writes a bench plan for a board, stage by stage: the stand-in for each part a breadboard cannot hold, what the breadboard cannot prove and which deck or board test proves it instead, the stand-ins for the controller's lines, the instruments, and for each test point the reading the decks predict with its span over the corners.
- **Evidence:** The reviewing engineer's breadboard notes for Last Hit v0.16 (the same branch) written again by the command: the stage-by-stage substitutes, the list of what a breadboard cannot prove, and each expected reading taken from a corner record.
- **Use case:** Bring a board up on the bench (a new use case).
- **Scope guard:** A stand-in comes from a table a person fills, each row with its source and what differs from the board's part. The command never invents an equivalence.
- **Status:** ready

### 4. Headless autoroute for hand-drawn boards
- **Promise:** `workcenter autoroute --apply <project>` reads any `.kicad_pcb` (footprints, pads, outline, nets, existing tracks) into the DSN writer that `kicadgen` already has, runs FreeRouting, merges the session into the board file, and the new fixture `route-me` passes DRC with 0 unconnected items afterwards, with no KiCad GUI step.
- **Evidence:** `tests/test_gates.py::test_autoroute_apply_routes_fixture` green in `make verify`; the fixture's DRC report attached to the PR.
- **Use case:** Route a board (`docs/USE-CASES.md`).
- **Scope guard:** No routing heuristics of our own. No GUI automation. The generated-design path already works (`workcenter design --route`); this item is the board-file parser in front of it. Zones and arcs may be out of scope for the first cut and must be reported, not silently dropped.
- **Status:** ready

### 5. Board gates as a reusable GitHub workflow for board repositories
- **Promise:** A board repository that adds 1 workflow calling `ThyFriendlyFox/via/.github/workflows/board-gates.yml@main` gets `workcenter gates` run on every PR, with the gates table in the job summary and a red check on a red gate.
- **Evidence:** A run link from a board repository, plus `tests/boards/pass-rc-divider` run through the workflow in this repository's CI.
- **Use case:** Review a board PR.
- **Scope guard:** No comments posted to the PR; the check and the summary are the output.
- **Status:** ready

### 6. MCP server for hosts that are not Claude Code
- **Promise:** `workcenter mcp` serves `doctor`, `gates`, `erc`, `drc`, `sim`, `export`, and `autoroute` as MCP tools over stdio, and the MCP inspector lists all 7 with their schemas.
- **Evidence:** An inspector screenshot and a test that drives the server with a scripted JSON-RPC session.
- **Use case:** Build another workcenter from this one.
- **Scope guard:** stdio only; no HTTP transport, no auth.
- **Status:** ready

## Later — candidates, not yet specced

- Copper pours in `kicadgen` — a zone per power net with `kicad-cli pcb drc --refill-zones`, so heater returns stop depending on 0.4 mm tracks.
- Pad-entry width check before routing — warn in `workcenter design` when a net class is wider than its narrowest pad allows.
- SIM gate from the schematic — export the SPICE netlist automatically and apply a stimulus template, so a project without a hand-written deck still gets a simulation.
- `workcenter new <name>` — scaffold a board project with the `.gitignore`, `sim/`, and a passing starter board.
- Publish the workcenter as an account-level Claude Code plugin — skills and the MCP server arrive in every cloud session without touching board repositories.
- BOM availability gate — `workcenter procure --strict` already fails on a line short of stock; a gate would run it before export. Needs a project-wide parts file first.
- Digi-Key API refresh for `procure` — re-read every Digi-Key row's breaks and stock through Product Information v4 with the user's own credentials, instead of page by page.
- STEP export in the EXPORT gate by default once the fixture proves it runs headless in CI within the time budget.
- Per-run output folders for the gates, or a lock on `build/`: two runs on one project at once mix their reports (M73).
- `workcenter sources --fetch` compares PDFs by their bytes; onsemi serves each download with a new trailer ID, so an unchanged datasheet reads as changed. Compare the page content, not the trailer.
- `workcenter placement route_check` at a heater class's widths (0.6 mm) fails links the router and the DRC pass on a dense board; let it take a class per net, as the DRC does.
- `workcenter verify` reads a calculation's verdict as written; an equation checker for the calculations (each numbered line recomputed) would close the gap that M71 fell into.
- `design --check` holds the board too: the committed board without its tracks and vias against the board the design file generates. Today it compares the schematic and the project file; a board whose outline was changed by hand to 30 x 20 mm passed the check and the fixture's test (a review of 2026-11-12).
- A first picture for a phone: at 390 px GitHub draws the README's first picture 324 px wide, and its code is 3.7 px high. A second capture with the 3 cards stacked, chosen by a `media` width in the `picture` element.
- A capture held to its page: `hero.png` is a capture of `hero.html`, and a test holds the page, not the picture. A record of the sources' hashes at capture time would fail a stale capture.
- The CLI's counts in the singular: `1 decks`, `1 errors, 1 warnings` are on the README's first screen.
- EXPORT's count of files: `22 gerber files` counts the drill file, the job file and 11 layers with nothing on them for a 2-layer board of 4 parts.
- Deck values held to the schematic: `kicad-cli sch export netlist --format spice` gives every R and C with its value, so a deck element named like a board reference can be compared with the part it models, a derated value needing its reason. Last Hit's decks write C5 as 2.5 uF in two decks and 4.7 uF in a third.
- A maker's own tolerances as corners: the `tolerance` fix deletes the LOT and DEV specs of a vendor model; kept as a side table they would move the model's internal parts too (`alter r.xu4.r1` reaches one). Last Hit's current sense crosses its bound inside 0 to 40 C once the monitor's 1.5 % is counted.
- What a model carries, declared: a `sources.csv` column, or a probe at 2 temperatures, saying whether a model has temperature in it, so a requirement that rests on one that has none is named. The gate today warns only when no measure of a whole deck moves.
- A requirement that rests on a model off its datasheet: a `warn` bound that fails names the model, and every traceability row whose deck includes that model would carry the name. Last Hit's REQ-REG-01 passes by 13 mV on a dropout its own warn bound calls wrong.
- Accepted warnings as a file the gates read: each warning a project keeps, with its reason, who accepted it and when, so `--strict` passes on those and fails on a new one or on an entry that no longer matches.
- Measures from ngspice's own data: a `wrdata` or raw file the gate reads, so a deck's `echo "vout = 2.5"` cannot stand for a measure.
- A rail's impedance deck written from the board: the capacitors with their ESR and bias, the track's resistance from `inspect resistance`, an inductance from its geometry, so the frequency plan's resonances are not typed by hand.
- Ratings as data: each part's absolute maximum, voltage rating and power in a parts column, so a pin's worst net voltage, a capacitor's derating and a resistor's dissipation are checked by a command, not in a calculation's prose.
- The board as one netlist: a generated schematic now carries its models (`d.sim`), so the SIM gate can export the board's netlist with `kicad-cli` and a deck becomes that netlist plus an overlay of sources and measures; the 12 retyped circuits of a project become 1. Until then nothing holds a deck to the board's parts: a small model's filter passed every gate with its op-amp written as 2 controlled sources in the deck. The design template now turns `check_sim` on, so the design file names each part's model or says why it has none; the deck is still typed by hand. On a copy of Last Hit v0.16 the exported netlist gave the current-sense reading of the hand-typed deck, 1.198 V at 27 C and 1.099 V at 85 C.
- A maker's model KiCad cannot read, at a path a schematic can name: the gate translates a vendor's file into `build/`, which is not committed, and `Sim.Library` needs a file the project keeps. A checked, translated copy beside the library row (its source, its fixes and its SHA256 recorded) would let `d.sim` name it; Diodes' current monitor file fails KiCad's parser as shipped.
- Every register of the RTL held to the netlist: SYNTH names a flop that the mapping removes, and says nothing of a flop that Yosys's `synth` pass removed before it. A view of the design before any cleaning would name each register bit the chip does not hold, for an answer in `chip.json`. 2 things make it more than a comparison of names: a state machine that Yosys writes with other bits, and a memory that becomes flops under other names.
- A part's pin map in its library row: a `Pins` cell in `sources.csv` (`1=VOUT 2=GND 3=EN 4=VIN`), so `d.sim` takes a part's binding from the row of its MPN and the map is written once, where the datasheet is open.

## Explicitly not doing

- Reverse engineering KiCad with REA or similar — KiCad is open source with an official IPC API and CLI. REA belongs to workcenters built on closed tools.
- GUI or screen automation of KiCad — every operation goes through `kicad-cli` or the IPC API.
- Bundling a patched KiCad — the workcenter installs the upstream PPA build or uses the upstream image.
- Installing `kicad-packages3d` by default — 3.3 GB for 3D models no gate reads.

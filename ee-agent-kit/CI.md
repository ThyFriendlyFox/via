# CI.md — what runs in `.github/` and why

The workflow files in `.github/workflows/` are the source of truth. This
file explains them and holds the repository settings that are not files.

| File | Trigger | Does |
|---|---|---|
| `ci.yml` | push to `main`, every PR, manual (`gh workflow run ci.yml --ref <branch>`: always `full`, the gate of a branch with no pull request) | `fast` on every change: no toolchain, `make verify-site` (KiCad's libraries hidden, no engine started). `full`: the image of this commit's toolchain when the registry gives it, else apt's package files kept from an earlier run (`tools/ci/apt_cache.sh`), `tools/ci/apt_archive.sh` (apt keeps the runner's mirror and Ubuntu's own archive, asks the fastest first, and in the index update sends a file to the next host after 15 s of silence), then `sudo env REQUIRE_FREEROUTING=1 APT_UPDATE_TIMEOUT=120 APT_DOWNLOAD_TIMEOUT=570 ./install.sh`; then `make verify` (tools/ci/README.md, "Where `full` runs"). `verdict` passes when `fast` passed and, for a change `tools/ci/scope.py` calls full, `full` too. |
| `nightly.yml` | 06:17 UTC daily | `tools/ci/apt_archive.sh`, then `sudo env REQUIRE_FREEROUTING=1 APT_UPDATE_TIMEOUT=120 APT_DOWNLOAD_TIMEOUT=570 ./install.sh` then `make verify`, always by install.sh. Keeps 1 `ci-failure` issue in step with the nights (`tools/ci/nightly_issue.py`): a failed night opens it or adds 1 comment with the run and the gate's `why:` lines; a passed night closes it with 1 comment naming the run; a second open one is closed as a duplicate of the oldest (tools/ci/README.md, "The nightly's `ci-failure` issue"). Catches a moved PPA, a new KiCad point release, a broken dependency. |
| `image.yml` | PR on the files the build reads, every push to `main`, `v*.*.*`, Monday 04:17 UTC, manual | Builds the image on amd64 and arm64 from install.sh, with CI's 2 bounds of its apt step as build arguments, checks it with doctor (its `requirements` row included: the venv holds the pins of the requirements.txt in the tag) and the gates on a fixture as the runner's user (they must write build/gates.json, and every file they write must be that user's); pushes to `ghcr.io/<owner>/via` except on a PR. |
| `board-gates.yml` | `workflow_call` from a board repository | `workcenter gates` on each project folder the caller names, 1 job each; the gates table in the job's summary; red on RED and SKIPPED. In the image of Via's toolchain where the runner can pull it, else `tools/ci/apt_archive.sh` then `install.sh` with CI's 2 apt bounds (`.claude/skills/board-ci/SKILL.md`). |
| `board-fixture.yml` | PR and push to `main` on the 2 board workflows, the fixture, `tools/`, `install.sh`, `requirements.txt` or `Dockerfile`; manual | Calls `board-gates.yml` on `tests/boards/pass-rc-divider` with `strict: true`, Via at the run's own commit. |
| `release.yml` | tag `v*.*.*` | Publishes the GitHub Release with generated notes (the image comes from `image.yml`). |
| `stale.yml` | Mondays | Marks issues stale after 60 days, closes after 14 more. `blocked`, `security`, `accepted` are exempt. |
| `../dependabot.yml` | weekly | pip (`requirements.txt`), GitHub Actions, Docker base image. Minor and patch updates grouped. |
| `../PULL_REQUEST_TEMPLATE.md` | every PR | What, Why, Evidence, checklist; the changelog line is a new file under `ee-agent-kit/changes/`. |

## Where the health gate runs

`main` takes no commit that its gate did not pass on that exact commit. The gate is `make verify` for a change `make scope` calls `full`, and `make verify-site` for one it calls `fast`. The full gate runs on GitHub, in the `full` job of `ci.yml`. It is the
same `make verify` as on a machine. The owner chose this on 2026-11-19.

| The change | Before its push | On GitHub | What may merge |
|---|---|---|---|
| Any change, pushed to a work branch with a pull request | `make check TESTS="<the test files of what it touches>"` | The push starts `ci.yml`. The `scope` job picks `fast` or `full`. `fast` runs on every change; `verdict` is green only when `fast` passed and, for a `full` change, `full` too. | The head commit, when `verdict` is green on it and the branch holds `main`'s tip. |
| A work branch with no pull request yet | `make check TESTS="..."` | A run by hand: `gh workflow run ci.yml --ref <branch>` (`workflow_dispatch`). It is always `full`. | Nothing merges without a pull request. A green `verdict` lets others start work from that commit. |
| A change `make scope` calls `fast`, pushed straight to `main` | `make verify-site` | The push to `main` runs `ci.yml`; its `fast` job runs `make verify-site` again. | It is on `main` already. |
| A release | The release commit goes through a pull request like any change. | Its `verdict` on `main`. | The tag goes only on a commit whose `full` job passed. A release commit is `fast`, so ask for a run by hand on `main`: `gh workflow run ci.yml --ref main` (RELEASING.md step 4). |
| Any change, where there is no CI (a fork without Actions, an offline machine) | `make verify`, alone on the machine (`ee-agent-kit/lead/gate-and-push.sh` pushes only on `VERIFY GREEN`) | Nothing. | The commit that printed `VERIFY GREEN`. |

`make check` is `make lint`, then the gate's kit checks (`make kit`, `verify/verify.sh kit`: the 2 copies of every kit skill, each skill's frontmatter, CLAUDE.md = AGENTS.md, every mistake's process and every process's Done when; 0.6 s to 0.75 s here), then pytest on the kit's own tests and the files in `TESTS`: the commits' authors (`tests/test_docs.py`), the 2 copies of the lead's skills (`tests/test_lead_skills.py`), and this rule's documents and kit checks (`tests/test_gate_rule.py`). Engine starts are refused and the tests marked `engine` are left out, as in `make verify-site`. It takes no lock, so it does not need the machine alone. With no `TESTS` it took 8.2 s to 14.5 s here, 3 runs on 4 processors with helpers at work (load average 5.2 to 6.5), on 2026-11-19.

When CI itself cannot run for a cause outside the change, the gate is `make verify` on the machine on the exact commit, by the same rule as a machine with no CI. On 2026-11-19 at 07:14 UTC a package host was down: `apt-get update` did not end within 120 s on the runner, 3 tries, and the job stopped before any test.

The rules that follow from it:

- A work branch may hold a commit the gate has not passed yet. The pull
  request shows it: its checks are pending or red. Nobody merges it,
  releases from it, or starts other work from it until `verdict` is
  green on that commit.
- A red `verdict` is answered with a new commit. Pushed history is not
  rewritten. A red gate is fixed, not left (AGENTS.md).
- A pull request's run tests its head merged with `main` as it was when
  the run started. Merge `main` into the branch first, so the tree CI
  tested is the tree that lands. If `main` moves before the merge, merge
  it in again and wait for the new `verdict`.
- Merge with `gh pr merge <number> --merge --match-head-commit <sha>`.
  GitHub then refuses the merge if the head is no longer the commit
  whose `verdict` you read.
- The gate's lock and the helpers' rules for it (PROCESSES.md P31 steps
  11 to 14) are for a gate on a machine. A landing that CI gates needs
  neither.
- `verdict` can be made a required check of `main` in the repository's
  settings (Branches). GitHub then refuses a merge without it. It is a
  setting, not a file; this document does not say whether it is on.

Why, from the runs of 2026-11-19. On the machine, the gate needs the
machine alone. The gate push24 waited 50 min 31 s for quiet and was
ended by its 1-hour limit (MISTAKES.md M273). The gate push28 ran
`make verify` in 906 s (its tests 889 s), from 05:26:16 UTC; the gate
before it, push27, had made its lock at 05:06:51 (M274, M278). While a
gate waits or runs, no helper may start a test. CI's `full` job ran the
same `make verify` on the same commit, 9beca5b, in 14 min 58 s (run
44466890200, 05:41:46 to 05:56:44 UTC, on the install path), while the
machine went on working. Inside the image, the `full` job of run
44428908528 took 12 min 42 s. Before this change each landing ran the
whole suite 2 times: on the machine, then on the pull request.

## Toolchain step

CI's `full` job takes the toolchain from the image of its tag when the
registry has it, else installs with `sudo env REQUIRE_FREEROUTING=1 APT_UPDATE_TIMEOUT=120 APT_DOWNLOAD_TIMEOUT=570 APT_OTHER_TIMEOUT=300 APT_FILE_RETRIES="$retries" APT_FILE_TIMEOUT="$seconds" APT_SLOW_PASS_COMMAND="$slow" ./install.sh`
(tools/ci/README.md, "Where `full` runs").

The 3 bounds end a stalled index or download with apt's own line within the `full` job's limit. Every download of install.sh now goes through the same bounded, watched passes: the main one within APT_DOWNLOAD_TIMEOUT, the openEMS step's and the boot step's each within APT_OTHER_TIMEOUT. Before, only the main one was; in the image build of job 135588402925 the openEMS step's download got 520 for libfparser4, went on, and the image was refused without openEMS, and in the passing job 135593285528 that download took 385 s with no bound. The arithmetic for the keeper, from job 135593285528's log: the steps no bound holds take 805 s (25 s before install.sh, 30 s to unpack and set up, 1 s for freerouting and java, 3 s for openEMS's libraries, 20 s after them, 725 s for `make verify`, 1 s after it). The bounds: 88 s for the key, 3 x 120 + 2 x 20 = 400 s for the update, 570 s for the main download, 300 s for the openEMS step's: 1358 s. 805 + 1358 = 2163 s, over the former 30 minutes (1800 s). The steps of apt's kept package files add their bounds, 360 s (below, "apt's package files kept between runs"): 2523 s. `timeout-minutes` of `full` is now 45 (2700 s): 177 s are left, room for `make verify` to grow (670 s on 2026-11-18, 725 s and 718 s on 2026-11-19). The boot step installs nothing on GitHub's runner (the passing run printed no `boot:` line); on the image's bare Ubuntu it adds its update, with the apt step's 3 tries and 2 waits (3 x 120 + 2 x 20 = 400 s), and a download of 300 s, and the image build keeps no package files: 2163 + 700 = 2863 s of the image build's 60 minutes (3600 s). The image build of job 135588402925 printed nothing for 271 s between `boot:` and its first Get, and `-qq` hid whether the update or the download took them: 1 try of 120 s could have refused that build. The nightly run (45 minutes, 2700 s) holds the same 2523 s. `test_the_worst_case_of_the_apt_step_fits_the_jobs_limit` reads each workflow's bounds and limit and holds this sum. A person's computer has no total bound. The download's 570 s cover all its passes and the waits between them (APT_DOWNLOAD_TRIES, default 5; APT_DOWNLOAD_WAIT, default 20 s), and the other downloads' 300 s each cover theirs, so the sum above holds them all. CI and the image build set neither variable and run on the script's defaults; `test_ci_and_the_image_build_leave_the_passes_and_the_wait_to_the_script` holds the 3 workflows and the Dockerfile to that.

CI's `full` job does not build the image. Before install.sh, the install path and the nightly run rank the hosts of Ubuntu's archive: `sudo env APT_ARCHIVE_CI=1 bash tools/ci/apt_archive.sh /etc/apt`. On 2026-11-19 each of 2 hosts was the slow one once. At 03:00 UTC the mirror us-east-2.ec2.archive.ubuntu.com crawled and the download hit its bound of 570 s, 3 runs (CI runs 44402154007 and 44432768560 had done the same). The answer then turned the mirror into archive.ubuntu.com; its first run on a runner, CI run 44444183056, passed, and the install step took 1 min 29 s. At 07:14 UTC run 44477966021 (job 135403130537) turned azure.archive.ubuntu.com into archive.ubuntu.com, and `apt-get update` did not end within 120 s in 3 tries. So the step now keeps every host: the mirror list (`/etc/apt/apt-mirrors.txt`) keeps the runner's mirror, archive.ubuntu.com and security.ubuntu.com, and a source that names a regional mirror itself is pointed at the list, with Ubuntu's own host added beside it. A probe asks each host for the first 1 MiB of `dists/<suite>/main/binary-<arch>/Packages.gz`, side by side, 3 s each and ended at 4 s: at most 5 s, of the 177 s the `full` job's limit leaves beside install.sh's worst case (2523 s of 2700). The list's priorities follow bytes a second; a host that does not answer goes last and stays; with no answer the list stays. `/etc/apt/apt.conf.d/80apt-archive-ci` sets apt's http and https timeout to 15 s and `Acquire::Retries` to 0, so in `apt-get update` a file whose host is silent for 15 s goes to the next host of the list at once (in the download, install.sh's own bounds on apt's command line take their place, and CI now passes them the same 0 and 15 s: below; job 135500622487 spent its whole 570 s on 1 pass from a host the probe had ranked first) (apt-transport-mirror(1); apt 2.8.3's `apt-pkg/acquire-worker.cc`). apt fetches 1 host's files in turn (`apt-pkg/acquire.cc`), the update puts 4 InRelease files on the first host, and a host that accepts and then says nothing costs 2 timeouts (`methods/basehttp.cc`). So a silent first host costs the update 60 s to 120 s; with apt's defaults (30 s, 3 retries) it would cost 508 s to 988 s. 120 s is all of 1 try of the update: a host that goes silent after the probe can still fail that try. The setting holds for every source: KiCad 10's PPA gets 1 try per update. The step prints 1 line per host with what it measured, and the order it chose. Setting the repository variable `CI_APT_UBUNTU_ARCHIVE` to `0` turns it off (tools/ci/README.md, "The hosts of Ubuntu's archive on the install path"). The rank is a first guess. Its first run on GitHub, CI run 44506767788 (job 135500622487), measured us-east-2.ec2.archive.ubuntu.com at 2468910 bytes/s and put it first; the download then got 48.3 kB/s from it, and 1 pass used the whole bound of 570 s. In that run install.sh's own `Acquire::Retries=3` and 60 s on apt's command line won over the 15 s rule; CI now passes it 0 and 15 s (below). But a host that keeps sending slowly fails no file, so no per-file rule moves it. So install.sh also watches each bounded pass: after 120 s (`APT_WATCH_WINDOW`) it ends a pass whose rate over its last 120 s, less its longest still stretch up to 60 s, would not fetch the rest of what apt said it needs within what is left of the bound, and the next pass follows after the wait. The install step sets `APT_SLOW_PASS_COMMAND` to `env APT_ARCHIVE_CI=1 bash tools/ci/apt_archive.sh --slow` (empty when `CI_APT_UBUNTU_ARCHIVE` is `0`), which puts the host that served the slow pass last in the mirror list before the next pass. To read a run: `[apt] Need to get <size> of archives.`, then, for a slow pass, `[install] apt: download pass 1 of 5 was too slow to finish: ... over the last 120 s, leaving out a pause of <s> s, from <hosts>; ...`, `[install] apt: APT_SLOW_PASS_COMMAND: ...` and `[apt-archive] /etc/apt/apt-mirrors.txt: <host> was too slow (a download pass too slow to finish, or an update try its bound ended); apt asks ...`; a stop names the hosts asked, the bytes and the rate.

The download now gives up a failed file's host as the update does. In job 135500622487, 151 files were asked again of the same slow host, because install.sh's own `Acquire::Retries=3` and 60 s on apt's command line won over the step's file. install.sh reads both from `APT_FILE_RETRIES` and `APT_FILE_TIMEOUT` (default 3 and 60 s, range-checked: 0 to 9 retries, 1 to 999 s), and the install step passes 0 and 15 through `sudo env` whenever it keeps the mirror list (3 and 60 when `CI_APT_UBUNTU_ARCHIVE` is `0`). A file that fails on KiCad 10's PPA, 1 host, then fails the pass, and the next pass asks for it again: 5 passes x 15 s + 4 waits x 20 s = 155 s of the 570.

The update names what stalled. Job 135588570683 ran 3 tries of 120 s, and its log said only that `apt-get update` of every package source did not end: `-qq` printed no line. The update now runs with `-q`, so apt prints a Hit, Get, Ign or Err line per index. A try its bound ends prints `[install] apt: update, try <n> of 3, did not end within 120 s (APT_UPDATE_TIMEOUT); the sources that had not answered (no Hit, Get, Ign or Err line): <address> <suite> (<the mirror list's hosts>), ...; apt's last <k> lines of that try:`, then apt's own last 10 lines at most. Before the next try it runs `APT_SLOW_PASS_COMMAND` with the silent mirror list's hosts in the order apt asks them (the lowest priority first, then the line: the rank step and `--slow` change only the priorities), so the host apt asks first goes last; a silent source of 1 host, KiCad 10's PPA, is simply asked again. The update gets no progress watch: its bound, 120 s, is 1 watch window, and the watch judges nothing before a whole window. A host that trickles is not named. apt prints `Get:` when a file begins to arrive and no line when it ends, so a host that sent its headers and then slowed or stalled has answered: the try names no source for it and the command does not move it. When every source printed a line, the cut try says so: `the sources that had not answered (no Hit, Get, Ign or Err line): none: each source printed a line, so a host that began a file and then slowed or stalled is not named and not moved`. CI's 15 s rule ends a stall that long, not a trickle. Job 135588570683's log, with `-qq`, cannot tell which case it was; the next cut try's last lines will.

## apt's package files kept between runs

The install path asks the package hosts for every file on every run. In job 135593285528 (2026-11-19) apt fetched 202 files, 343372502 bytes (the sum of its `Get:` lines): 282899198 bytes from Ubuntu's hosts and 60473000 bytes in 4 files from KiCad 10's PPA. That day 3 runs of 1 pull request failed on a package host. So `full`'s install path and the nightly run now keep apt's `.deb` files between runs, and a run asks the hosts only for what changed (`tools/ci/apt_cache.sh`, actions/cache).

What is kept: the `.deb` files of `/var/cache/apt/archives`, in a folder of the runner's user, `$RUNNER_TEMP/apt-archives`. Before install.sh, actions/cache restores that folder, and the script copies each regular `.deb` file of that folder itself into apt's folder with `sudo cp`. A link, a folder (and any `.deb` inside it, such as `partial/`) or a file of another kind stays out; a kept folder that is itself a link gives nothing. install.sh does not change: apt finds the files where it always looks, as on a person's computer, and its sandbox user `_apt` downloads into `partial/` as before. Pointing apt at another folder was not chosen: it needs an option on every apt command of install.sh, a folder `_apt` may write, and install.sh's watch counts `APT_ARCHIVES`.

The key: `apt-archives-v1-<runner OS>-<arch>-<ID>-<VERSION_ID>-<hash>-<ISO week>`, for example `apt-archives-v1-Linux-X64-ubuntu-24.04-81232a8313d66b5c-2026-w47`. The hash is the first 16 hex digits of the SHA256 of the lines of install.sh that decide what apt fetches: each `*_PACKAGES=(` and `*_LIBS=(` list to its `)`, the PPA's address, and every line that runs `apt-get install` (13 lines today). A comment elsewhere does not change it. The week makes a new save each week, as packages are updated upstream. Without its own key, a run restores the newest save of the same hash, else the newest of the same runner and release. GitHub returns "the most recently created cache" of a prefix (GitHub's page "Dependency caching reference", "Cache key matching").

Who saves: a push to main, the nightly run and a run by hand, after a good install. A pull request's run restores and never saves: the save step's condition names the events, and the script refuses any other. GitHub scopes a pull request's save to its merge ref anyway, and a run of a stranger's code should write nothing others read. A run restores from its own branch and from the default branch; a pull request also from its base branch (same page, "Restrictions for accessing a cache"). The 3 saving events are on that page's list of trusted triggers ("Cache access for low-trust workflow triggers"). A key is written once: a run that restored its own key saves nothing.

What a restored file can do. apt 2.8.3 takes a file already in its folder by its size alone, not its hash (`apt-pkg/acquire-item.cc`, pkgAcqArchive, lines 3494 to 3512, from salsa.debian.org's tag 2.8.3). A truncated or partial file has another size: apt removes it and fetches it again. A file of the right size and other bytes would be installed. This has been read in apt's source, not yet shown on a runner: the machine that built this has no apt documentation (`/usr/share/doc/apt` holds only the changelog, NEWS and copyright), and nothing here runs apt. A run by hand on a throwaway branch shows it: after a hit, overwrite 1 restored file with as many other bytes before install.sh. apt takes it by its size when install.sh's log has no `Get:` line for it and the check prints its `SHA256 ..., but apt's index says ...` line; a `Get:` line for it would show that apt checks a kept file's hash after all. So after the install, whether it passed or failed, the step "Check apt's package files" holds every `.deb` in apt's folder to the SHA256 that `apt-cache show <package>=<version>` gives from apt's signed indexes. A forged file most likely breaks the install, so the check names it then too. A file whose bytes differ fails the run with 1 line and saves nothing. The check comes after the install: it names such a file, it does not stop its use. That is why only runs of main's own code save.

What is dropped before a save: the kept folder is made anew from the files that matched. A file no index lists any more (a version the PPA or Ubuntu replaced) has no SHA256 there and leaves the cache. `apt-get autoclean` keeps a file by its name and version alone (`apt-pkg/clean.cc`, lines 72 to 123) and does not read its bytes; the check does both. Expected size: about 343 MB a save, from job 135593285528's sum, more when a week brings new versions before the old ones go. GitHub's limits: 10 GB for all caches of a repository; entries not used in 7 days are removed; past the limit, the least recently used go first (same page, "Usage limits and eviction policy", "Default limits"). Weekly saves of 343 MB stay far below 10 GB.

The bounds: the restore 2 minutes, the copy 1, the check 1, the save 2: 360 s, in the worst case of `full` (2523 s of 2700) and of the nightly run. The restore, the copy and the save never fail the run (`continue-on-error`); a cut restore leaves at worst a short file, which apt fetches again. The key step reads 13 lines (0.013 s here).

What a run's log shows, 1 line each:

- The key step: `[apt-cache] key: <key>; without it, the newest save of <prefix>, else of <prefix>`.
- The restore step: actions/cache's own `Cache restored from key: <key>` or `Cache not found for input keys: ...`.
- The copy: `[apt-cache] restored <n> files, <bytes> bytes, into /var/cache/apt/archives`, or `restored 0 files: <folder> is not there (no save of this key or its fallbacks); apt gets every file`, or `restored 0 files: <folder> is a link, not a folder; apt gets every file`.
- install.sh: `[apt] Need to get <to fetch>/<all> of archives.` names what apt still fetched and the whole size (apt-private/private-install.cc:311-316). On a full hit the first size is 0; with nothing restored apt prints 1 size, `Need to get <all> of archives.`
- The check: `[apt-cache] checked <n> files in /var/cache/apt/archives against apt's signed indexes: <m> match, <k> that no index lists are left out`, then `[apt-cache] saving <n> files, <bytes> bytes, under <key>`, or `not saved:` and why (a failed install, a pull request, the restore found this key itself, no key). After a failed install the check line comes first all the same.
- The save: actions/cache's `Cache saved with key: <key>`.

## What CI still needs from a third party

CI's `full` job still needs Launchpad's host on every run that takes the install path. The owner chose the container image to end that: the `full` job runs in the image of its toolchain's content tag when the registry has it, and needs no third party then (`tools/image.py decide`). What stays open: a pull request that changes `Dockerfile`, `install.sh` or `requirements.txt` takes the install path, as its test, and needs Launchpad's host; and every push to main runs install.sh again inside the image build, so an outage of KiCad 10's package source turns that `Image` run red and leaves `main`'s image stale. Building the toolchain layer from install.sh and requirements.txt alone, kept between builds by the registry's cache, would let a push that changes neither run without a third party; it is not built.

The install path also needs Ubuntu's archive. It keeps the runner's mirror, archive.ubuntu.com and security.ubuntu.com (ports.ubuntu.com on an arm machine with a regional mirror) and asks the fastest first, since each was the slow one once on 2026-11-19 (CI runs 44402154007 and 44432768560, then 44477966021). Every host slow or down at once still turns the install path red, and so does a host that trickles without a silence of 15 s, or a first host that accepts and goes silent after the probe; KiCad 10's source has 1 host. The image path does not use the runner's apt.

The image holds node (Ubuntu 24.04's `nodejs`, 18.19.1), so a change to the forms' functions, the lead's workflow scripts, the nightly's issue step or their tests takes the image path like any other change.
